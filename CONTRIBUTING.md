# Contributing

This fork serves two goals, and almost any contribution lands under one of them:

1. **Recover retail 1.14d** — turn `Game.exe` back into C++ and make the rebuild
   byte-match the original binary. That work lives **upstream** at
   [jaenster/redivivus](https://github.com/jaenster/redivivus); its
   [CONTRIBUTING.md](https://github.com/jaenster/redivivus/blob/main/CONTRIBUTING.md)
   is the door.
2. **Improve beyond retail** — the Vanilla+ layer: crash fixes players feel, the
   widescreen resolution ladder, opt-in quality-of-life. That is **this repository**,
   [VTSTech/D2VP-QoL](https://github.com/VTSTech/D2VP-QoL), and the rest of this file
   is about it.

A finding filed in the wrong place is still a finding — it only costs a redirect. When in
doubt, [open an issue here](https://github.com/VTSTech/D2VP-QoL/issues/new/choose) or
[ask on Discord](https://discord.gg/xQXpH5Nj5).

## If you want to help recover retail 1.14d

Go upstream. [Redivivus](https://github.com/jaenster/redivivus) recovers `Game.exe`
function-by-function from Ghidra databases and checks the result against the original
binary with a byte-match harness. Byte-matching itself is out of scope for this fork.
Most of the upstream tree is **generated** (files
begin `// Auto-generated by ghidra-mcp - DO NOT EDIT`), so a fix to a name, type, function
boundary or the emitted C++ has to land upstream of the generator, not in its output.

| | |
|-|-|
| **Generated** - edits are overwritten | everything under `Source/`: the module directories (`Source/D2Client/`, `Source/D2Common/`, `Source/D2Game/`, `Source/Fog/`, ...), the shared headers in `Source/D2Headers/`, `Source/modules.cmake`; the global data in `Source/globals/`; also `3rdparty/Storm/` and `3rdparty/crashy/` |
| **Hand-written** - pull requests welcome | `project.json` (the module table), `Redivivus/`, `3rdparty/libbacktrace/`, `3rdparty/implibs/`, `cmake/`, `docs/`, `asm_matching/`, `tools/`, `agent/`, `CMakeLists.txt`, `.github/`, `README.md` |

Upstream's
[CONTRIBUTING.md](https://github.com/jaenster/redivivus/blob/main/CONTRIBUTING.md)
covers that workflow end to end: which door a finding takes (issue template vs agent
proposal), the evidence ranking (strongest first: the developers' own words, the paired
function on the Mac build, typed field accesses, referenced strings — inference last), and
how the read-only Ghidra MCP server lets an AI agent read the databases and file
corrections addressed **by address**.

Two boundary notes so nothing gets double-filed:

- A **crash you can reproduce while playing** is a Vanilla+ fix here first (below) — and
  if the root cause turns out to be a reconstruction bug (a wrong type, a lost value), it
  belongs upstream too. File both and cross-link them.
- A change that makes the build **match retail more closely without changing what players
  feel** (names, comments, byte-match figures) is upstream-only — byte-matching is not
  work this repo hosts.

Fixes landed upstream arrive here at the next sync — this fork tracks ahead of upstream,
never behind, and [docs/merge-upstream.md](docs/merge-upstream.md) documents the merge
protocol (eight numbered syncs so far).

## If you want to improve the game (Vanilla+)

This is the repo for that. The layer sits directly in the recovered source: crash fixes,
the six-stop resolution ladder (1344x700 / 1366x768 / 1920x1080 included), the Vanilla+
Options page, and the opt-in feature set — shared stash, alt-toggle labels,
shift-item-compare, auto gold pickup and the rest ([FEATURES.md](FEATURES.md) is the full
slate). The client ships as **`d2vp.exe`**; the Vulkan `glide3x.dll` lives in its own
repo, [Glide3xVK](https://github.com/VTSTech/Glide3xVK).

### The house rules

These invariants keep the fork mergeable with upstream. The gate suite
([`tools/check-vanilla-plus.sh`](tools/check-vanilla-plus.sh), currently **519 checks**)
enforces most of them mechanically:

1. **Vanilla by default.** With no `d2vp.ini` (or a missing key) the game behaves like
   retail 1.14d. Every feature ships **OFF**, reads a `[features]` key, hot-re-reads it
   every ~2 s, and has a row on the Vanilla+ Options page.
2. **No balance changes, no save-format changes.** `.d2s`/`.d2x` layouts stay untouched;
   the shared stash keeps its own `_d2vp_shared.sss` and character files stay
   retail-compatible.
3. **Fork edits are marked.** Edits inside upstream files ride between `// VP-BEGIN` and
   `// VP-END` markers; new code goes in fork-only TUs
   (`D2Client/UI/VanillaPlusCore.{h,cpp}` and friends). Upstream files stay free of new
   code so the next sync merges clean.
4. **Every source change updates the gate.** New feature, new anchor, new marker — add
   the gate rows that pin it, and the suite stays green.
5. **LF everywhere.** Merged `main` is LF-normalized; detect and preserve each file's
   ending, never mix.
6. **The build identifies itself.** The self-ID string in `Game/Main.cpp` bumps every
   code round; `d2boot.log` line 1 pins any exe to its round.
7. **Single-player only.** Not designed, tested or supported for Battle.net. The repo
   holds **no game data** — no assets, no MPQs, no copyrighted content from the original;
   you build and run against your own 1.14d installation.

### Fixing a crash

Crash reports are the most valuable contributions this project gets — the D3D fullscreen
boot crash and the Gheed gamble click-crash both started as one. To attribute a crash
correctly, collect **both** artifacts from one repro:

| Artifact | Comes from | Tells us |
| --- | --- | --- |
| `d2crash-<date>-<time>.txt` | `d2vp.exe` (symbolised, written next to the exe) | the crashed module, function and offset |
| `glide3x.log` | the glide3xvk wrapper | what the wrapper was doing; whether the faulting thread was wrapper code |

Rule of thumb: faulting frame in `glide3xvk`/`vk_backend`/slang →
[Glide3xVK](https://github.com/VTSTech/Glide3xVK) issue; faulting frame in
`D2*`/`Storm`/`Fog` with a d2crash report → issue here (and upstream too, if it reads like
a reconstruction bug). A crash without both artifacts cannot be attributed — attach the
first line of `d2boot.log` as well, so the build is pinned.

### Proposing a feature

Check [FEATURES.md](FEATURES.md) first — the slate scopes what is plausible and what is
already ruled out. Then open an issue describing the behavior you want, not the
implementation. What lands with a feature:

- an opt-in `[features]` key and an Options-page row (rule 1),
- gate rows pinning its anchor/marker surface (rule 4),
- [SMOKE-CHECKLIST.md](SMOKE-CHECKLIST.md) checks if it changes something a player sees,
- one short entry in [CHANGELOG.md](CHANGELOG.md).

### Building and testing

[docs/building.md](docs/building.md) has the full toolchain story; the short version:

```sh
cmake -S . -B build -G Ninja -DCMAKE_TOOLCHAIN_FILE=cmake/mingw-i686.cmake
cmake --build build
```

On Windows, `tools/build-local-win11.ps1` sets up MSYS2's i686 toolchain and runs the same
gates CI runs. GitHub CI builds every release tag and ships the stripped
`d2s-<sha>.exe` plus the linker map (load-bearing for crash symbolisation). Run
[`tools/check-vanilla-plus.sh`](tools/check-vanilla-plus.sh) before opening a PR — it is
the suite CI enforces, and green is the bar.

### PR checklist

- [ ] gate suite green (`tools/check-vanilla-plus.sh`)
- [ ] fork edits marked (`VP-BEGIN`/`VP-END`) or confined to fork-only TUs
- [ ] new feature = ini key + Options row + gate rows (+ SMOKE checks if visible)
- [ ] CHANGELOG carries one short entry
- [ ] LF endings preserved; self-ID bumped if the PR is a code round
- [ ] SP-only scope respected; no game data added

### The docs lanes

Human-facing docs stay short: [README.md](README.md), [CHANGELOG.md](CHANGELOG.md),
[SMOKE-CHECKLIST.md](SMOKE-CHECKLIST.md). The engineering detail lives in the agent lane:
[FEATURES.md](FEATURES.md) (the slate), [handoff.md](handoff.md) (the live work log),
[HISTORY.md](HISTORY.md) (the verbatim archive) and [plans/](plans/). A behavior change
puts one line in the human lane and the detail in the agent lane.
