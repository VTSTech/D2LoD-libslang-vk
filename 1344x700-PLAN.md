# 1344x700 — resolution-mode plan (video-options stop 3)

*Drafted 2026-11-05 (R108 docs round) on owner ask. Owner framing, recorded: "From what I
understand 1344x700 was planned by Blizzard in the original game, but never implemented or
shipped." The tree agrees with the mechanism half: retail binaries carry mode-3 plumbing end
to end, but no UI stop ever exposed it. Slate row 14 in [FEATURES.md](FEATURES.md); the
1080p follow-up is row 15. Companion record for the 1280x720 round this rides on:
[docs/resolution-widelayout-audit.md](docs/resolution-widelayout-audit.md).*

Status: **PLANNED — no code yet.**

---

## 1. Goal and non-goals (v1)

**Goal.** A third stop on the video-options resolution slider: **1344x700 — retail's own
dormant mode 3**. Opt-in by picking the stop, exactly like the Vanilla+ 1280x720 stop
(sites-1..6 round, field-proven 2026-10-30). Not `[features]`-gated; the default stop and
every existing registry value are untouched.

**Non-goals for v1:**
- No front-end (main-menu) re-layout pass — the same watch-item the 720p stop carries;
  in-game UI is the scoped surface.
- No 1920x1080 (FEATURES.md row 15, its own round; this round's leftovers feed it).
- No summit-cloud tiling fix — the 1344-wide right-edge gap predates us (retail behavior).
- No ini gate, no Vanilla+ Options page row — resolution is a video-options stop, not a
  feature toggle.

## 2. Invariants

- **I-parity**: not picking the stop changes nothing. A new build with an old registry runs
  the same mode it always did (positions 0-2 keep their meaning — see §4).
- **I-wide-class**: 1344x700 renders through the SAME wide-UI class as retail 800x600 and
  Vanilla+ 1280x720 — one rigid 800-px UI unit centered on the playfield (offsets X 272 /
  Y 100, both formula-computed), zero new UI math.
- **I-contract**: mode index 3 keeps retail's meaning in every table, renderer, and the
  wrapper interface (`Glide3xVK g3x_resolution_size` entry 17 was already reserved for it).

## 4. Design — two gaps

**Gap A — `CLIENT_SetScreenResolution` case 3** (the only in-game chain gap). Insert after
the `case 2:` block (:469-475), before `case 4:`:

```c
case 3:
  {
    // Vanilla Plus: retail's dormant 1344x700 (mode 3)
    ScreenSizeX = 1344;
    ScreenSizeY = 700;
    nScreenMode = 1;
    break;
  }
```

Everything downstream (`WindowSizeX/Y`, `D2GFX_SetVideoMode(3)`, border type, automap
recenter) is the retail flow the `case 4:` block already rides.

**Gap B — slider, four edits in `EscMenu.cpp`:**

1. `UI_SLIDER_ApplyResolution` (:58817): position→mode mapping becomes 0→mode 0, 1→mode 2,
   2→mode 4, **3→mode 3**. Append semantics: positions 0-2 keep their meaning, so a 720p
   registry value must not re-number.
2. `UI_SLIDER_LoadAndApplyResolution` (:58901): attach a second Route-B blank into
   `pDC6SubImages[3]`, `nSubImageCount = 4` (comment update).
3. `UI_SLIDER_DrawResolutionValue` (:58840): generalize the single-stop guard
   (`nImageIndex != 2` early-return) into a per-stop label table — `{2: L"1280x720",
   3: L"1344x700"}`. The right-align + `RESLABEL_DESCENDER_COMP` math (issue #23
   conventions) is label-agnostic already; only the guard and the text change.
4. Static row entry (:32357): comment-only (loader count stays 2 — it needs an MPQ DC6 per
   static stop; both VP stops attach at runtime).

**Registry semantics.** `SReg "Diablo II\Resolution"` stores the slider POSITION. Missing →
1 (800x600), unchanged; foreign/out-of-range → clamp to the largest stop (:58917, already
generic). Back-compat falls out for free: a position-3 registry on a pre-plan build clamps
to 720p. No migration, no new key.

**Pre-work check (none needed this round):** the R92 dims-pair tests
`(1280,720) || (1344,700)` in Glide.cpp ×2, Direct3D.cpp ×2 and Windowed.cpp already cover
mode 3 everywhere. Consolidating them into one shared predicate is deferred to the 1080p
round (row 15), where the list would otherwise start growing per mode.

## 5. QA / field loop

Matrix: Glide {fullscreen, `-w`} × {fresh 1344x700, 800x600→1344x700 switch, 1344x700→720p
switch}; D3D fullscreen same; DDraw best-effort — an 8-bit 1344x700 fullscreen display mode
may not exist on modern systems (the same hardware caveat class 720p carries; record the
outcome, don't block on it).

In-game checklist (the 720p field loop, re-run): HUD re-centered (272/100), orbs + skill
grids + belt hit-tests, inventory / waypoint / quest log / help at the wide offsets,
inventory coord-cache refetch on mode switch (the wide-flag cache key), automap margins,
cutscene round-trip (restore via the site-2 table), Alt+Tab, Save & Exit → relaunch keeps
the stop. SMOKE §H additions only if the belt pass is due anyway.

## 7. Risk

**Low–Med.** The delta is two files plus a label table; every renderer path mode 3 touches
was field-proven by the 720p round (whose three dispatch defects were renderer-side, all
fixed). The known-unknowns are the same class as any renderer round: hardware/display-mode
quirks (DDraw 8-bit) and the front-end menus — both out of scope v1, both recorded at the
field round.
