## 1. Goal and non-goals (v1)

**Goal.** A third stop on the video-options resolution slider: **1344x700 — retail's own
dormant mode 3**. Opt-in by picking the stop, exactly like the Vanilla+ 1280x720 stop
(sites-1..6 round, field-proven 2026-10-30). Not `[features]`-gated; the default stop and
every existing registry value are untouched.

**Non-goals for v1:**
- No front-end (main-menu) re-layout pass — the same watch-item the 720p stop carries;
  in-game UI is the scoped surface.
- No 1920x1080 (FEATURES.md row 15, its own round; this round's leftovers feed it).
- No summit-cloud tiling fix — the 1344-wide right-edge gap predates us (retail behavior).
- No ini gate, no Vanilla+ Options page row — resolution is a video-options stop, not a
  feature toggle.

## 2. Invariants

- **I-parity**: not picking the stop changes nothing. A new build with an old registry runs
  the same mode it always did (positions 0-2 keep their meaning — see §4).
- **I-wide-class**: 1344x700 renders through the SAME wide-UI class as retail 800x600 and
  Vanilla+ 1280x720 — one rigid 800-px UI unit centered on the playfield (offsets X 272 /
  Y 100, both formula-computed), zero new UI math.
- **I-contract**: mode index 3 keeps retail's meaning in every table, renderer, and the
  wrapper interface (`Glide3xVK g3x_resolution_size` entry 17 was already reserved for it).

## 4. Design — three gaps

**Gap A — `CLIENT_SetScreenResolution` case 3** (the only in-game chain gap). Insert after
the `case 2:` block (:469-475), before `case 4:`:

```c
case 3:
  {
    // Vanilla Plus: retail's dormant 1344x700 (mode 3)
    ScreenSizeX = 1344;
    ScreenSizeY = 700;
    nScreenMode = 1;
    break;
  }
```

Everything downstream (`WindowSizeX/Y`, `D2GFX_SetVideoMode(3)`, border type, automap
recenter) is the retail flow the `case 4:` block already rides.

**Gap B — slider, four edits in `EscMenu.cpp`:**

1. `UI_SLIDER_ApplyResolution` (:58817): position→mode mapping becomes 0→mode 0, 1→mode 2,
   2→mode 4, **3→mode 3**. Append semantics: positions 0-2 keep their meaning, so a 720p
   registry value must not re-number.
2. `UI_SLIDER_LoadAndApplyResolution` (:58901): attach a second Route-B blank into
   `pDC6SubImages[3]`, `nSubImageCount = 4` (comment update).
3. `UI_SLIDER_DrawResolutionValue` (:58840): generalize the single-stop guard
   (`nImageIndex != 2` early-return) into a per-stop label table — `{2: L"1280x720",
   3: L"1344x700"}`. The right-align + `RESLABEL_DESCENDER_COMP` math (issue #23
   conventions) is label-agnostic already; only the guard and the text change.
4. Static row entry (:32357): comment-only (loader count stays 2 — it needs an MPQ DC6 per
   static stop; both VP stops attach at runtime). The second attach mirrors the existing
   guard shape (count-check before attach), so menu re-inits don't stack blanks.

**Gap C — `SetupMiniPanel` mapping** (MiniPanel.cpp:671, two-line edit). The game-enter
and cutscene-exit restore keeps its own registry-position copy: clamp `nResolution > 2 → 1`
(:680-682) and mapping `>= 2 → 4` (:687-688). Position 3 must be valid before the clamp and
tested before the `>= 2` arm:

```c
if (nResolution < 0 || nResolution > 3) {   // was: > 2
  nResolution = 1;
}
// ...
} else if (nResolution == 3) {
  nScreenMode_lcl = 3; // Vanilla Plus: dormant 1344x700 (must precede the >= 2 arm)
} else if (nResolution >= 2) {
  nScreenMode_lcl = 4; // Vanilla Plus: 1280x720
}
```

Note for the code round: the existing CI gate `resolution: minipanel clamp + mode 4`
(check-vanilla-plus.sh:281) pins `nResolution > 2` — it must flip to `> 3` in the same
commit or the suite red-arms.

**Registry semantics.** `SReg "Diablo II\Resolution"` stores the slider POSITION. Missing →
1 (800x600), unchanged; foreign/out-of-range → clamp per-path (all already generic). On a
post-fix build every path honors position 3. On a PRE-plan build a stray position-3 clamps
to the largest known stop per path — 720p via the video-options load clamp (:58917),
800x600 via the old MiniPanel clamp — harmless retail-shaped behavior either way. No
migration, no new key.

**Pre-work check (none needed this round):** the R92-family dims-pair tests
`(1280,720) || (1344,700)` already cover mode 3 everywhere — seven copies across five
files: Glide.cpp ×2 (:2757, :2820), Direct3D.cpp ×2 (:4673, :4779), DirectDraw.cpp ×1
(:2021), Windowed.cpp ×1 (its own named helper `RENDERER_GDI_IsWideUiLayout`, :1208-1211),
and client-side VanillaPlusCore.cpp ×1 (:602, the PANELSHIFT gate). Consolidating them into
one shared predicate is deferred to the 1080p round (row 15), where the list would otherwise
start growing per mode.

## 9. Field round 1 record (2026-11-05) — the D3D switch crash

**Report** (owner, with a Glide screenshot): "works in Glide, but crashes upon switching
in D3D" — the stop works end to end under glide3xvk 0.4.6 (video menu at 1344x700, world
renders, wide-UI offsets correct), but selecting it under the Direct3D renderer exits the
process.

**Root cause — not the mode-3 code.** The D3D renderer carried 1344x700 all along (size
case `RENDERER_D3D_GetWindowSizeByResolutionMode` :2268-2270, wide-set :2591, dims
guards :4673/:4779). The failure is in the exclusive display-mode change every D3D
resize rides: `RENDERER_D3D_InitializeDevice` → DD7 `SetDisplayMode(1344, 700, 32)`.
Since Vista, that request only accepts timings from the driver's display-mode list;
**1344x700 is a non-standard timing retail never shipped, so no driver lists it**, while
1280x720 (CEA standard) enters everywhere — which is why the 720p round never hit this.
The rejected mode-set fails init, and D2Win's `D2GFX_SetVideoMode` treats a failed resize
as fatal ("Failed to resize window... this is fatal!" → `exit`). Glide is immune because
the wrapper sizes its own Vulkan swapchain and never changes the display mode.

**Fix — two layers, one candidate set (exact mode, else 1366x768, else 1360x768):**

1. **Renderer ladder** (`D2Direct3D/Renderer/Direct3D.cpp`, InitializeDevice): a rejected
   `SetDisplayMode` retries the two smallest standard host modes that fully contain the
   logical frame. Viewport and every render coordinate stay 1344x700, so the larger flip
   chain shows as inert black letterbox bands; `RENDERER_D3D_ClearBackbuffer` now clears
   the LOCKED surface's row count (byte-identical for exact-fit modes, band hygiene for
   hosts). Dims-agnostic: also hosts a hypothetical unlistable 1280x720. Covers boot and
   any path that bypasses the client choke point.
2. **Client probe** (`D2Client/ClientModeInGame.cpp`, in the `CLIENT_SetScreenResolution`
   choke point — covers slider apply, game-enter and cutscene-exit re-applies): stops
   3/4 on DDraw/D3D first require the driver's 32-bpp mode list (`EnumDisplaySettingsA`)
   to contain the exact mode OR a host mode; otherwise the switch is refused cleanly —
   screen keeps the running mode and the saved slider position snaps back to the matching
   stop (registry/slider/screen agree; the game-enter re-apply can't loop on a dead
   stop). Glide skips the probe. No path that survives the probe can reach the fatal
   resize.

**Result**: D3D users get 1344x700 letterboxed inside a host mode their driver lists (the
normal case), or a clean refusal with everything left coherent — never the exit. DDraw
users get the probe (no DDraw ladder — a larger primary would garbage the BltFast frame,
so refusal is the honest behavior there). **Gates**: 7 new `res3:` D3D/probe rows →
401/401. **Owed**: llvm-mingw build gate, D3D field re-test (expect: enter 1344x700 →
mode-set rejects → ladder logs and letterboxes at 1366x768; check the flip-chain bands
are black and the mouse stays confined to the 1344x700 area).

### §9.1 Field round 2 — "doesn't crash, but D3D shows a borderless window" (R110 → R111)

**Report** (owner): the crash fix held — "that kinda worked. doesn't crash" — but
launching D3D fullscreen and switching to 1344x700 displayed **a borderless window
instead of fullscreen**.

**Root cause — the second emulation behavior.** The R110 ladder only fired on a
REJECTED `SetDisplayMode`. The Win10/11 DDraw fullscreen emulation can also ACCEPT a
mode it cannot actually set (fake success, no error to react to) and fall back to a
borderless window at the requested size on the unchanged desktop — so on the field box
`SetDisplayMode(1344, 700, 32)` "succeeded", the ladder never fired, and the emulation's
fallback is exactly the reported look. (And had the ladder fired, R110's follow-up
`MoveWindow(0, 0, 1344, 700)` would still have shrunk the game window inside the
1366x768 host mode, leaving the desktop peeking past the window's right/bottom edges —
the other half of the same look.)

**Fix — probe-first presentation + host-sized window (R111):**

1. **Probe BEFORE the mode-set** (`D2Direct3D/Renderer/Direct3D.cpp`): new file-local
   `VPRES3D_IsDisplayModeListed` (twin of the client helper — separate module, own copy;
   shared predicate deferred to the dims-pair refactor round). The doomed
   `SetDisplayMode(1344, 700, 32)` is never called when the driver's list omits it: an
   unlisted stop goes straight to the first LISTED host mode (1366x768 → 1360x768, same
   candidate set, now a real mode-set every time — no fake-success zone). The flip chain
   (created without DDSD_WIDTH/HEIGHT) auto-sizes to the host display mode; viewport and
   render coordinates stay logical; bands stay black via the R110 locked-rows clear.
2. **The window covers the HOST**: hosted stops `MoveWindow` to the host size — under
   the emulated fullscreen the game window is what covers the screen, so it must be
   host-sized. True exclusive paths (exact mode listed) stay retail byte-identical.
3. **Client probe hardened** (`D2Client/ClientModeInGame.cpp`): depth-aware base
   `VPRES_IsDisplayModeListedAtDepth` + a **DirectDraw exact-only branch** — DDRAW's
   8-bit pipeline has no letterbox mechanism, so it enters stops 3/4 only when the
   driver genuinely lists the mode at 8 bpp (extinct on modern drivers → graceful
   refusal; closes the same-class crash DDRAW still carried after R109/R110).
